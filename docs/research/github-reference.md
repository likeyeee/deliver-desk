还做了一次 [Patchright](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-python) 兼容驱动的只读试验，仍出现 `code=37`，因此没有把它加入项目依赖，也没有把这次试验计为修复成功。

## 已确认的原因

1. 实站曾反复跳到 `/web/passport/zp/security.html?code=37`，再返回职位页或首页。输入框会在导航中重建，因此之前的“关键词未生效”错误没有说明真正原因。
2. 原代码只检查页面可见的验证文字，可能漏掉很快消失的安全页。现在记住主页面的安全跳转和正常搜索请求返回的 `36/37`，同一任务的详情页也会停止操作。
3. 普通 Chrome 的登录和工具专用目录的登录是不同会话。登录入口改为网站的登录页，并等账号入口与页面稳定后才报告完成。每次任务在同一个浏览器会话内先校验登录，再进入搜索；需要扫码时，登录后自动继续该任务。
4. 普通 Chrome 中已实测搜索 `AI应用`，选择泉州和“经验不限”；筛选结果 URL 包含 `experience=101`，界面显示选中标签。代码据此修正选中值的核对范围。
5. 后续专用登录页实际跳到了 `about:blank`，而旧二维码截图仍存在，造成扫码状态误判。现在离开登录页即移除二维码截图，持续空白页会快速停止并报告环境异常；这不等于已经解决网站拦截。
6. 普通 Chrome 的真实操作发现：点击“立即沟通”可能只创建会话，没有己方文字消息。代码将建会话与文字发送分开，默认改为发送配置模板；文字需要完整己方气泡及“送达/已读”回执。遇到对方“不合适”回复不继续追加模板。
7. 聊天页的“查看职位”实测会新开对应的职位详情页。代码补充此路径核对职位 ID，避免只能依赖聊天页直接链接。此分支已纳入合成页面测试，尚未完成 Playwright 实站验证。

失败任务关闭自己的页面前，会尽力保存 `.boss-cli/last-error/diagnostics.json` 和截图。诊断中只保留地址路径及允许的搜索/错误参数，不保存 Cookie、安全令牌或完整 HTML。截图保存在本机私有数据目录。

本轮真实发送由 Computer Use 的原生 Chrome 控制完成，并以 `cua_assisted` 登记到同一个历史库：一条文字送达，另一条仅建立沟通后收到不合适回复。它验证了实际网站步骤与本地记录/去重；没有把它作为 Playwright 环境修复成功的证据。
